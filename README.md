# vtslides

Slides written in Typst that morph in the browser.

You lay out whole pages in Typst and wrap whatever should move in
`#mark("key")[…]`. One `.typ` compiles to a PDF and an HTML deck that are
pixel-identical; in the HTML, a marked element that appears on two adjacent
pages travels from one place to the other — position, size, colour — using the
browser's own View Transitions API. An object that changes with a parameter (a
curve at the next phase, a pendulum at the next pose) is interpolated on its
SVG nodes by the Web Animations API. There is no interpolation code of our own:
the runtime navigates, tidies the DOM once at load, and hands the browser two
states.

```sh
typst compile --root . --features html,bundle --format bundle examples/demo.typ examples/out
#   → examples/out/demo.pdf + examples/out/demo.html   (one compile, both formats)
```

Open `examples/out/demo.html` in a browser (double-clicking the file works — no
server needed). Only one format:

```sh
typst compile --features html --format html demo.typ demo.html
typst compile --features html               demo.typ demo.pdf
```

Requires Typst 0.15 (`html`, `bundle`) and a browser with same-document View
Transitions including transition types and `view-transition-class`; the deck is
verified in Chromium.

## What you write

```typst
#import "@preview/vtslides:0.1.0": *

#let body = {
  slide[
    #set align(center + horizon)
    #mark("title")[#text(size: 72pt, weight: 700)[Marks, not coordinates]]
  ]

  slide[
    #mark("title")[#text(size: 40pt, weight: 700)[Marks, not coordinates]]
    The title got smaller and moved to the top-left corner — and the source
    contains no coordinates.
  ]
}

#bundle(name: "demo", title: "My talk", body)
```

Both pages are ordinary Typst layout; the only addition is `#mark("title")`
around the thing that should morph. The geometry is *measured* from the layout
at load time, never written by hand:

```
slide 1:  m-title  30.3% 34.6%  39.4% × 13.8%
slide 2:  m-title   4.7%  6.5%  21.9% ×  7.7%
```

`bundle` is the entry point for `--format bundle`; its top level cannot hold
content directly, so `let` the content first. For a single format use `deck`
directly: `#show: deck.with(title: "My talk")`.

The full API reference is generated by [tidy](https://typst.app/universe/package/tidy)
from the `///` comments in `lib.typ`: `typst compile --root . docs/api.typ docs/api.pdf`.

## Three words

The test is one sentence: **did the layout change, or is one object moving?**

- **Transition** — the layout's state changed: a new page, or the next frame of
  the same page (one more line, the title moved). Runs on View Transitions: the
  browser snapshots the old and new layout and interpolates marked elements
  pairwise by key. `slide(..frames)`, `deck(transition:)`, `mark(key)[…]`.
- **Element animation** — one object varies with a parameter: a sine wave at the
  next phase, a vector rotated, a ball at its next position. The layout is
  unchanged; the object's own geometry moves. Runs on Web Animations, on the
  SVG nodes. `mark(key, s0, s1, …)` gives the states explicitly and steps
  through them with the keys.
- **Continuous animation** — again an object moving, but on its own, without
  keys: `slide(anim:)`, running as long as the page rests on that frame.

## API

| | |
| --- | --- |
| `bundle(name:)` | Base name of the outputs, `<name>.pdf` + `<name>.html`. Every other named argument goes to `deck`. |
| `deck(title:)` | Document title. |
| `deck(width:, height:)` | Layout size, default 1280pt × 720pt. The PDF page size; each HTML frame reads `page.width` / `page.height`, and the player's aspect ratio follows. |
| `deck(pdf:)` | Target of the toolbar's download link. `auto` = the `.pdf` with this file's name, `none` = no button, a string is used as is. `bundle` fills it in. |
| `deck(duration:)` | Transition duration in milliseconds, default 700. Adjustable live with `-` / `=` / `0`. |
| `deck(transition:)` | Default **page-to-page** transition: `"fade"` (default, crossfade), `"slide"` (horizontal push — forward, the new page comes in from the right), `"rise"` (vertical push), `"wipe-left"` / `"wipe-right"` / `"wipe-up"` / `"wipe-down"` (reveal, named by the direction the front travels), `"none"`. Governs unmarked content only; paired marks morph regardless. Not used between frames of one page, which always crossfade. |
| `deck(theme:)` | Light/dark theme of the player chrome (toolbar, overview, speaker view): `auto` (follows the system), `"dark"`, `"light"`. The layout's colours are Typst's. |
| `deck(fill:)` | Layout background, default `#111318`. The PDF uses `page(fill:)`; the HTML paints the same value under the slides and thumbnails, independent of the chrome theme. |
| `deck(font:)` | Font stack with glyph-by-glyph fallback, default `("DejaVu Sans", "Noto Sans CJK SC")`. |
| `slide(title:)` | Shown only in the thumbnail caption, never in the layout. May be content. |
| `slide(note:)` | Speaker notes. HTML only; read by the speaker view (`s`). May be content. |
| `slide(..frames)` | Several bodies = **frames of the same page**. Navigation walks them one by one; the overview merges them into one thumbnail. |
| `slide(transition:)` | Overrides `deck(transition:)` for this page: how the whole page comes in when turning to it. Going back, the page being left decides, so it always replays in reverse. |
| `slide(anim:)` | Continuous animation, `key → spec`, where the spec is Web Animations keyframes + options. See below. |
| `mark(key)[…]` | Names a piece of content. The same key on two adjacent pages pairs them. |
| `mark(transition:)` | This mark's **own** enter/leave effect (same names as above). Applies only when the mark is one-sided in a transition; a paired mark morphs regardless. Unset, the mark folds into the page. |
| `mark(key, s0, s1, …)` | **Element animation**: N states of one object, stepped with `→` / `←`. The PDF shows the last state. |

`window.vtslides` exposes `{ go, next, prev, index, total, step, steps, speed, deck }`
(`step` is writable) and dispatches `vt:slide` on `.vt-deck` on every move.

## Frames and positions

```typst
#let base = [ … ]
#slide(title: "Two frames", base, base + [ #mark("eq")[$ … $] ])
```

Frames still transition with View Transitions, so "the second frame has one
more line" is an element-level interpolation, not a page jump — what `#pause`
is meant to look like, without parsing the content. In the PDF each frame is a
page, as in a handout.

To the audience a frame and an element-animation step are the same thing —
"press once, advance one notch" — so a page's **positions** are its frames and
steps flattened into one sequence. `#9.3` in the address bar is page 9, third
position; the toolbar counter, the overview dots (one per position), the
progress bar and the speaker view's "next step / next page" all count the same
way. Going back from a later page lands on the last position of this one.

## Element animation

```typst
#let wave(t) = cetz.canvas({
  import cetz.draw: circle, line, rect, content
  rect((-0.5, -1.7), (8.5, 1.7), stroke: none)          // pin the bounding box
  line(..range(0, 41).map(i => (i * 0.2, amp(t) * calc.sin(1.2 * i * 0.2 - 0.5 * t))))
  circle((1.4 * t, …), radius: .25, fill: …)
  content((4, -1.4), [t = #t])
})
#slide(title: "Element animation")[
  #place(dx: 120pt, dy: 200pt, mark("wave", ..range(0, 6).map(wave)))
]
```

Several bodies in one `mark` are the states of one object. `→` moves to the
next state, `←` back along the same path, and the page turns only once the
states are exhausted.

This is not a crossfade of snapshots. The SVG nodes of two states are compared
one by one, and every property that differs — the path's `d`, `transform`,
`fill` / `stroke`, `stroke-width`, `opacity`, `x` / `y` / `width` / `height` —
is a CSS property handed to `el.animate()`: the curve bends into the other
curve, the ball slides to its new position, the colour blends. Duration and
easing are the transition's (`deck(duration:)`, `-` / `=`).

So the states must be **the same drawing under different parameters**: the same
structure, the same number of elements, only the numbers differ — a function
`f(t)` fed a few values of `t`. States whose element count changes fall back to
a plain switch (with a console warning); so does a `d` whose command count
changes. Text changes glyphs and switches. If the canvas's bounding box differs
between states the origin jumps, so pin the extent with an invisible rectangle
first.

## Continuous animation

```typst
#slide(
  anim: (
    dot: (follow: "track", duration: 4000),
    spin: (keyframes: ((transform: "rotate(0)"), (transform: "rotate(1turn)")), duration: 6000),
  ),
)[
  #place(dx: 120pt, dy: 180pt, mark("track")[#cetz.canvas({ … line(..pts, close: true) })])
  #place(dx: 120pt, dy: 180pt, mark("dot")[#std.circle(radius: .3cm, fill: green)])
  #place(dx: 900pt, dy: 300pt, mark("spin")[#std.rect(width: 90pt, height: 90pt)])
]
```

The spec is not a DSL of its own: it is Web Animations keyframes + options
(`duration` in ms, `easing`, `direction`, `iterations` — infinite and linear by
default), passed to `el.animate()` as is; see MDN. Keyframes come from one of
three places:

- `keyframes` animates the mark itself (transform, opacity, …). The bouncing
  balls are five marks with five such animations: piecewise `easing` for
  gravity, a `scale` squash on the landing frame, `delay` to stagger them.
- `follow: "track"` runs the mark's centre along the first `<path>` of another
  mark on the same frame (a ball on a track), via CSS `offset-path` — on the
  compositor, only `offset-distance` moves. `orient: true` turns it with the
  tangent.
- Neither, and the `mark` of that key carries several states: the states are the
  keyframes. The N poses one piece of code computed are played continuously,
  one animation per node, read exactly like a step of an element animation. The
  double pendulum is 96 poses integrated with RK4 in Typst and played with
  `anim: (double: (duration: 8000, direction: "alternate"))`; the sea is 25
  states of three stacked sines, first and last equal, looping seamlessly. A
  mark named this way counts no steps, and the PDF shows its first state.

Animations start once the page transition has finished, pause when the frame
is left or the overview opens, and do not play under `prefers-reduced-motion`.

## CeTZ

`cetz.canvas(…)` exports native SVG `<path>`s; wrapped in `mark()` it pairs by
key like text does.

- One key for the whole canvas: position and size interpolate, the content
  crossfades.
- Elements that should move separately: one small canvas and one key each.
- A `mark` inside a canvas works too — `content((x, y), mark("dot")[#std.circle(…)])`
  nested in an outer `mark("wave")` is lifted out of the outer snapshot and
  interpolated on its own. (Not inside the states of an element animation:
  those nodes are compared one by one and stay put.)
- For the object itself to move, use an element animation:
  `mark("wave", ..range(0, 6).map(wave))`.

A transition interpolates boxes, not paths: a 30° rotation shows as two
snapshots crossfading, and a curve does not bend into another curve. Bending is
the element animation's job.

Two things to know: the canvas's bounding box follows what is drawn, so a ball
at +1.2 on one frame and −1.2 on the next moves the box's edges and the origin
jumps frame to frame — draw an invisible `rect(…, stroke: none)` first to pin
it. And CeTZ has a `mark` of its own (arrow heads), so `import cetz.draw: *`
shadows vtslides' `mark` (`expected content, found array`); import by name.
Inside a canvas block, `circle` is CeTZ's as well — Typst's is `std.circle`.

## Presenting

| Key | Action |
| --- | --- |
| `→` `↓` `PageDown` `Space` `Enter` `n` `j` | Next position: next step / next frame / next page |
| `←` `↑` `PageUp` `Backspace` `p` `k` | Previous position (from a later page, lands on this page's last position) |
| `Home` / `End` | First / last page |
| `1`–`9` | Jump to a page |
| `f` | Full screen |
| `o` / `a` | Overview. Click a thumbnail to open it; hover or click the dots in its corner to preview / open a position |
| `l` | Laser pointer |
| `-` / `=` / `0` | Slower / faster / reset (a factor on every duration, kept in `localStorage`) |
| `s` | Speaker view |
| Wheel | Next / previous page — one notch per page with a mouse, one gesture (inertia included) per page on a trackpad; in the overview it scrolls the grid |
| Click / swipe | Left third goes back, the rest goes forward; swipe left / right on touch. Clicks during a transition count |

The toolbar in the bottom-right corner (counter, overview, laser, PDF, full
screen) hides after 2.4 s without mouse movement. The PDF button is a real
`<a download target="_blank">`, so it never navigates the deck away
mid-presentation.

The **overview** shows one thumbnail per page: the current frame if you are on
that page, otherwise the finished page (last frame, last step). Opening a page
from it zooms that page into place; turning pages morphs elements. Those are
two different transitions, and the overview uses the first.

The **laser pointer** is a system cursor with a mouse (drawn by the compositor,
so it never lags) and a DOM dot on touch or pen (there is no pointer to style),
chosen per event by `pointerType`. While it is on, taps and swipes do not turn
pages.

The **speaker view** (`s`) opens a separate window you can drag to another
screen: progress bar, current page, next page, notes, a timer (click to reset)
and its own toolbar. The two previews are iframes loading this same HTML at a
`#page.position` hash, so frame transitions and animation steps play there as
they do on stage. Keys, buttons, clicks and the wheel in that window drive the
main window; with the laser on, pointing at the current-page preview shows the
dot on the main window. It works over `file://` and closes with the main
window.

## How it works

**Identity is a label.** `mark(key)` attaches the Typst label `vt-key` to a box
around the content. Typst's SVG export writes a label as a `<g data-typst-label>`
*wrapping* the content, so the subtree is the boundary — nothing is inferred
from geometry. On the PDF side a label costs nothing, so no code is gated by
backend.

**Hoist.** `view-transition-name` is silently ignored on SVG children (only
elements in the CSS box tree are captured), so `hoist.js` runs once at load:
it measures each marked `<g>` in the page's viewBox (`getBBox` × CTM, read as
a ratio of two `getScreenCTM`s so the result is resolution-independent),
creates an absolutely positioned `<svg>` host with that viewBox and a
`view-transition-name`, and moves the `<g>` into it. Glyphs stay in the page's
`<defs>` and are referenced with `<use>`; nothing is copied. Everything is
measured before anything is moved, so nested marks stay correct.

**Pairing is the browser's.** On every page turn the runtime calls
`document.startViewTransition({ update, types })`; the browser pairs
`::view-transition-old(name)` and `::view-transition-new(name)` by string
equality and interpolates the box. There is no diff, no content matching. Names
are unique only among elements rendered *together* (other pages are
`display: none`), so the same key on every page is fine — and the same key
across N consecutive pages is one object moving N−1 times, each transition
starting where the previous one ended. Names carry an occurrence index
(`m-title-1`, `m-cell-2`), so a key may appear several times on one page.

**Split and merge.** A key that appears once on this frame and three times on
the next splits into three; three to one merges. One name pairs one couple, so
the runtime clones the shorter side for the duration of the transition and
removes the clones when it finishes. Any counts work, not just 1 ↔ N.

**Nesting.** `#mark("outer")[… #mark("inner")[…] …]` forms two groups; the
browser lifts the inner one out of the outer snapshot, as the API specifies.

**A transition is a pair.** The way the next frame enters is the way the
previous one leaves: fade in / fade out, push in from the right / push out to
the left, reveal from the bottom / cover from the bottom — at every instant the
two make up one page. Each effect in `deck.css` is one such pair, keyed on
`html:active-view-transition-type(<effect>)` with the distance or edge in
`--vt-in` / `--vt-out`; going back swaps the two, so reverse is the mirror for
free. `old` and `new` are composited with `plus-lighter`, so a crossfade stays
at constant brightness.

**Page-to-page vs. within a page.** The page-level effect (`deck` /
`slide(transition:)`) is used only when turning to another page. Between frames
of one page the layout stays put and changes incrementally, so root crossfades
and each element's own entrance is `mark(transition:)`. A one-sided mark with
an effect of its own gets a `vt-fx-<effect>` class for the transition; one
without folds into the page (its name is removed for the duration) and moves as
part of the whole sheet.

**Fidelity.** `html.frame` outputs glyph outlines (`<path>`, no `<text>`), so
rendering is Typst's own and independent of installed fonts. The PDF and the
HTML compiled from one bundle are compared pixel by pixel by `tools/verify.mjs`;
what remains is anti-aliasing of two rasterisers.

## Limitations

- **Z-order changes**: hoisted regions are painted above the page. A marked
  element that was under other content comes out on top.
- **Overflow is clipped silently**: a page is a fixed-size block; content that
  does not fit is invisible in both the PDF and the HTML, identically, but
  nothing warns.
- **Mid-transition is a bitmap**: View Transition snapshots are textures, so a
  large size change is blurry halfway and sharp at both ends — like any magic
  move.
- **Glyph-level morphing** between two marks is out of scope; at that grain
  each glyph must be animated by hand.

## Files

```
typst.toml          package manifest
lib.typ             entry point: deck / slide / mark / bundle
deck.css            page SVG layout, slide switching, overview, transition pairs, toolbar, laser
hoist.js            lifts marked <g>s into HTML-level <svg> hosts with a view-transition-name
runtime.js          navigation, element-animation steps, continuous animation, toolbar, laser, overview zoom, speaker view
examples/demo.typ   the example deck
docs/api.typ        API reference, generated by tidy from lib.typ
tools/check.mjs     region geometry at four window sizes, pairing chains, clone clean-up, console errors
tools/verify.mjs    PDF ↔ HTML pixel comparison, frozen mid-transition frames
tools/ui.mjs        toolbar / laser / overview / touch / transitions / element & continuous animation / speaker view
```

`tools/` need `playwright`; `verify.mjs` also needs `pdftoppm` (poppler) and
`compare` (ImageMagick). To inspect a transition, take over
`document.startViewTransition`, `await vt.ready`, then pause and seek every
animation from `document.getAnimations()` — a screenshot taken on a timer is
hundreds of milliseconds late and makes any transition look like a jump.
